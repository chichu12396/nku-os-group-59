## 三、实验整体逻辑分析

> 本章回答两个问题：这一章按照什么主线展开；各个功能为什么要按这个顺序实现。

### 3.1 本章节的逻辑主线

#### 3.1.1 一句话概括

本章围绕“**让内核能够响应突发事件**”展开。Lab2 让内核能够管理物理内存，但内核仍然是一条“从 `kern_init` 一直往下执行”的直线；本章要让它具备在任意时刻被硬件打断、保存现场、进入 C 语言处理、处理完再**正确回到被打断的位置**继续执行的能力。

这条主线可以拆成五个环节：

```
能产生 Trap → 能保存上下文 → 能进入 C 处理 → 能恢复上下文 → 能正确返回
```

任何一个环节缺失，后面的环节都无法验证：没有保存就无法恢复；没有恢复就无法返回；没有正确的 `epc` 就会反复触发同一条异常。

#### 3.1.2 完整链路

```
kern_init()
  ├─ idt_init()          stvec = __alltraps；sscratch = 0
  ├─ pmm_init()          Lab2 的物理内存管理就绪
  ├─ idt_init()          再次确保 Trap 入口有效
  ├─ clock_init()        sie.STIE = 1；sbi_set_timer(now + 100000)；ticks = 0
  └─ intr_enable()       sstatus.SIE = 1
          │
          │  约 10 ms 后，定时器到期
          ▼
硬件（S 态 Trap 响应）
  ├─ sepc     ← 被打断指令的地址
  ├─ scause   ← 0x8000000000000005（最高位 1 表示中断，低 63 位 5 表示 S 态定时器）
  ├─ sstatus.SPP  ← 陷入前的特权级（本实验为 S，即 1）
  ├─ sstatus.SPIE ← 陷入前的 SIE
  ├─ sstatus.SIE  ← 0（进入 Trap 后先关中断）
  └─ pc       ← stvec = __alltraps
          │
          ▼
__alltraps（C 负责的入口）
  ├─ SAVE_ALL：sp -= 288，把 x0..x31（x2 单独处理）和 sstatus/sepc/sbadaddr/scause
  │             按 struct trapframe 的布局写入内核栈
  ├─ mv a0, sp        // a0 = Trap frame 地址
  └─ jal trap         // 调用 C 函数；ra = __trapret 的地址
          │
          ▼
trap(tf)
  └─ trap_dispatch(tf)
       ├─ (intptr_t)tf->cause < 0  → interrupt_handler(tf)
       └─ (intptr_t)tf->cause ≥ 0  → exception_handler(tf)
          │
          ▼
__trapret
  └─ RESTORE_ALL（A 负责）
       ├─ sstatus ← tf->status；sepc ← tf->epc
       ├─ 恢复 x1、x3..x31
       └─ 最后恢复 x2（陷入前的 sp）
          │
          ▼
sret
  ├─ pc    ← sepc
  ├─ 特权级 ← SPP
  └─ SIE   ← SPIE
```

#### 3.1.3 为什么是这几个 CSR

| CSR | 在本实验中的作用 | 不这样做会怎样 |
|---|---|---|
| `stvec` | Trap 入口地址，`idt_init()` 写入 `__alltraps` | 硬件不知道跳到哪里，Trap 无法进入内核 |
| `sepc` | 保存被打断/触发异常的指令地址；`sret` 从它恢复 PC | 无法回到原执行流；handler 修改 `epc` 也失去意义 |
| `scause` | 说明 Trap 原因；最高位区分中断/异常 | 无法分类处理，只能一律 panic |
| `sstatus.SIE` | S 态中断总开关 | 为 0 时硬件不会响应可屏蔽中断 |
| `sstatus.SPIE` | 进入 Trap 时保存旧的 SIE；`sret` 时恢复到 SIE | 返回后中断使能状态错误，可能丢中断或意外开中断 |
| `sstatus.SPP` | 记录陷入前的特权级 | `sret` 可能返回到错误的特权级 |
| `sscratch` | `SAVE_ALL` 用它暂存陷入前的 `sp`，随后清零 | 没有临时寄存器保存旧 `sp`；清零后还能识别“Trap 发生在内核态”的递归异常 |
| `sret` | 与上述 CSR 成对出现，完成返回 | 只能用 `mret` 或手工跳转，语义不正确 |

这些 CSR 不是孤立存在的：**硬件在进入 Trap 时写一组，`SAVE_ALL` 把它们抄到栈上，C 代码通过 Trap frame 读写，`RESTORE_ALL` 再写回 CSR，最后 `sret` 消费它们**。整个实验的“上下文管理”就是围绕这组寄存器展开的。

#### 3.1.4 `scause` 最高位是中断/异常的分水岭

RISC-V 规定：`scause` 最高位为 1 表示**中断**（异步），为 0 表示**异常**（同步）。因此：

- `0x8000000000000005`：最高位 1，低 63 位 5 → S 态定时器中断；
- `0x0000000000000003`：最高位 0，低 63 位 3 → 断点异常；
- `0x0000000000000002`：非法指令异常。

`trap_dispatch()` 用 `(intptr_t)tf->cause < 0` 来判断：把无符号数转成有符号数后，最高位为 1 就是负数。B 的 `interrupt_handler()` 再用 `cause & ~(1 << 63)` 取出真正的中断号。这个“最高位”设计把中断和异常放在同一个 CSR 里，硬件只需要一个原因寄存器。

#### 3.1.5 Trap frame 是三方共享的唯一契约

Trap frame 是本章最重要的数据结构。它由三部分代码共同遵守：

1. **汇编保存**：`SAVE_ALL` 规定布局，并把寄存器写进去；
2. **C 处理**：`trap()`、`interrupt_handler()`、`exception_handler()` 通过 `struct trapframe *` 读写；
3. **汇编恢复**：`RESTORE_ALL` 按同一布局读出来，写回寄存器和 CSR。

布局如下（RV64，`REGBYTES = 8`）：

| 偏移（字节） | 内容 | 偏移（字节） | 内容 |
|---|---|---|---|
| 0 | `x0/zero` | 152–248 | `s3`..`t6` |
| 8 | `x1/ra` | 256 | `sstatus` |
| 16 | `x2/sp`（来自 `sscratch`） | 264 | `sepc` |
| 24–248 | `x3`..`x31` | 272 | `sbadaddr` |
| — | — | 280 | `scause` |

总大小 36 × 8 = **288 字节**，与 `SAVE_ALL` 的 `addi sp, sp, -36 * REGBYTES` 完全一致。

两个容易出错的细节：

- **`x2(sp)` 与其他寄存器不同**：`SAVE_ALL` 先把陷入前的 `sp` 存进 `sscratch`，等 32 个通用寄存器都存完后，再用 `csrrw s0, sscratch, x0` 把它取出来存到 offset 16。因此 `RESTORE_ALL` 也必须**最后**恢复 `sp`，因为此前所有 `LOAD` 都要用当前 `sp` 寻址。
- **`sstatus` 与 `sepc` 要写回 CSR，而不是只恢复通用寄存器**：B 的异常处理会修改 `tf->epc`（让 PC 前进到下一条指令），A 的 `RESTORE_ALL` 必须把修改后的值写回 `sepc`；否则 `sret` 仍回到原指令，异常无限循环。

#### 3.1.6 时钟中断为什么必须“重新上弦”

`clock_init()` 做了两件事：

```c
set_csr(sie, MIP_STIP);          // 允许 S 态定时器中断
clock_set_next_event();          // sbi_set_timer(rdtime() + 100000)
```

`sie.STIE` 只是“允许”这类中断，它本身不会产生事件；真正决定“下一次什么时候触发”的是 `sbi_set_timer()`。硬件在定时器到期时产生一次中断，但**不会自动安排下一次**。所以 `interrupt_handler()` 每处理一次时钟中断，都必须再调用一次 `clock_set_next_event()`，否则系统只会收到一次时钟中断。

`timebase = 100000`，QEMU 的 `timebase` 是 10 MHz，所以 100000 个周期 = 10 ms，即 100 次/秒；`TICK_NUM = 100`，所以每 100 次（约 1 秒）打印一行 `100 ticks`。`ticks` 被声明为 `volatile size_t`，因为它在中断处理函数里被修改、在主循环里被读取，编译器不能把它缓存在寄存器里。

#### 3.1.7 本章与 Lab2 的衔接

Lab2 的物理内存管理已经就绪：`pmm_init()` 建立页分配器，`alloc_pages()`/`free_pages()` 维护空闲链表。这些操作必须是原子的，否则中断可能插在“取出链表头”和“更新链表头”之间，破坏数据结构。框架用 `local_intr_save()`/`local_intr_restore()` 在临界区内关中断：

```c
local_intr_save(intr_flag);   // 若 SIE=1，则关中断并记录 flag=1
/* 操作空闲链表 */
local_intr_restore(intr_flag); // 仅当之前是开的，才重新开中断
```

这正是本章“Trap 机制”与 Lab2“内存管理”的交汇点：**Trap 让内核能响应外部事件，而临界区让内核在响应事件时不被另一件事打断**。

### 3.2 功能的逐步实现

#### 3.2.1 第一步：先读懂 `SAVE_ALL` 与 `struct trapframe`

**做了什么**：读 `SAVE_ALL` 的 36 条 `STORE`，对照 `struct trapframe` 的字段顺序，确认每个偏移的含义。

**为什么先做这个**：Trap frame 是汇编保存、C 处理、汇编恢复三方共享的契约。布局理解错了，后面写的每一行代码都建立在错误的前提上。特别是 `x2` 的特殊处理（来自 `sscratch`、必须最后恢复）和四个 CSR 字段的位置（32/33/34/35），是后面所有代码的“地基”。

**不做的后果**：`RESTORE_ALL` 会按错误偏移取值，Test 1 的寄存器现场全部错乱；`__alltraps` 可能把错误的地址传给 `trap()`。

#### 3.2.2 第二步：实现 `RESTORE_ALL` 与 `__alltraps`，搭起闭环

**做了什么**：

- `__alltraps`（C）：`SAVE_ALL` 之后执行 `mv a0, sp` 和 `jal trap`，把 Trap frame 指针按调用约定传给 `trap()`；
- `RESTORE_ALL`（A）：先写回 `sstatus`/`sepc`，再恢复 `x1`、`x3`..`x31`，最后恢复 `x2`。

**为什么先做这个**：没有“进入 → 保存 → 调用 C → 恢复 → 返回”的闭环，任何 handler 都无法被验证。即使 `interrupt_handler()` 写得完全正确，如果 `RESTORE_ALL` 没有恢复 `sp` 或没有写回 `sepc`，系统也回不到被打断的代码，测试根本跑不完。

**两个必须守住的不变量**：

1. `__alltraps` 中 `jal trap` 前后 `sp` 不变。`RESTORE_ALL` 完全依靠 `sp` 相对偏移寻址；`sp` 一旦改变，所有 `LOAD` 都会读错位置。
2. `RESTORE_ALL` 必须把 `tf->epc` 写回 `sepc`。B 的 handler 修改的是栈上的 `tf->epc`，不写回 CSR 就等于没改。

**如果不这样做的后果**：

- `sp` 被改动：Trap frame 偏移全部错位，寄存器恢复成垃圾值，可能直接跑飞；
- `sepc` 没写回：`sret` 回到触发异常的指令，再次触发同一个异常，形成死循环、串口刷屏。

#### 3.2.3 第三步：实现 `interrupt_handler()` 与 `exception_handler()`

**做了什么**：

- `interrupt_handler()`：按 `cause & ~(1 << 63)` 区分中断号。时钟中断先 `clock_set_next_event()` 重新上弦，再 `ticks++`；每 `TICK_NUM` 次打印统计；累计打印达到 `SHUTDOWN_AFTER` 后关机。其他中断按类型输出提示；未知中断用 `print_trapframe(tf)` 兜底。
- `exception_handler()`：`CAUSE_ILLEGAL_INSTRUCTION` 和 `CAUSE_BREAKPOINT` 输出规定格式的信息，并让 `tf->epc` 前进该指令的长度；其他异常用 `print_trapframe(tf)` 兜底。

**为什么接着做这个**：有了闭环，才能“处理并返回”。时钟中断是唯一能周期性触发的 Trap，是验证闭环最方便的手段；异常则验证“修改 `epc` 后能否正确返回”。

**关键点**：

- 时钟中断不重新上弦 → 只收到一次，Test 3 无法达到 200 ticks；
- 异常不推进 `epc` → 返回后重复执行同一条指令，死循环；
- 异常推进长度错误 → 跳过或落入指令中间，Test 1/2 失败。

#### 3.2.4 第四步：用三种场景验证，并理解 `epc` 的步长

**做了什么**：用时钟中断、断点、非法指令三类 Trap 验证整个机制。

| 测试 | 触发的 Trap | 覆盖的能力 | `epc` 前进量 |
|---|---|---|---|
| Test 1 | `ebreak`（被汇编为 2 字节的 `c.ebreak`） | 26 个寄存器的保存/恢复、断点返回 | **2 字节** |
| Test 2 | `.word 0x0000007b`（4 字节非法指令） | 非法指令处理、handler 兜底 | **4 字节** |
| Test 3 | S 态定时器中断 | 持续中断、重新上弦、Trap 反复返回 | 不涉及（中断返回原指令） |

**为什么不能固定加 4**：RISC-V 的压缩指令（C 扩展）是 16 位，普通指令是 32 位。`ebreak` 在默认工具链下被汇编成 `c.ebreak`（机器码 `0x9002`，2 字节），而测试里的非法指令 `.word 0x0000007b` 是 4 字节。如果统一加 4，断点测试会跳过 `ebreak` 后面的一条指令，导致 Test 1 失败。

**正确的判断方法**：读取 `epc` 处指令的低两位：

```c
uint16_t insn = *(const volatile uint16_t *)tf->epc;
tf->epc += ((insn & 0x3) == 0x3) ? 4 : 2;
```

低两位 `11` 表示 32 位指令；否则是 16 位压缩指令。

**如果不这样做的后果**：

- 固定加 4：Test 1 的 `li a0, 0x105` 被跳过，后续 `bne` 比较失败，返回 `1`，测试报 `FAIL (register context)`；
- 固定加 2：非法指令只前进了半个指令，下一次取指会落在指令中间，产生新的非法指令，可能无限异常。

#### 3.2.5 第五步：理解关中断、临界区与原子性

**做了什么**：看 `pmm.c` 里的 `local_intr_save/restore` 如何保护空闲链表操作。

**为什么最后理解这个**：它不参与“一次 Trap 的闭环”，但解释了“为什么 Trap 机制必须和同步原语配合”。在单核上，关中断是最小粒度的互斥：只要 `SIE = 0`，当前 hart 就不会响应可屏蔽中断，临界区内的多条指令就能原子完成。`__intr_save()` 返回“之前是否开着中断”，使临界区可以嵌套：内层恢复时不会误开中断。

**与本章的关系**：Trap 是“打断”的来源，临界区是“暂时不接受打断”的手段。两者一开一关，构成内核并发控制的最基础一对概念。

#### 3.2.6 为什么必须是这个顺序

```
读懂布局 ──→ 保存/恢复/入口闭环 ──→ handler 处理 ──→ 三类场景验证 ──→ 临界区与并发
   (地基)          (骨架)              (血肉)            (验收)             (延伸)
```

后一步都依赖前一步：没有布局就无法写恢复；没有闭环就无法验证 handler；没有 handler 就无法产生可观测的输出；没有验证就无法确认步长、重新上弦这些细节。反过来，如果先写 handler 再补 `RESTORE_ALL`，handler 的输出可能根本回不到原执行流，调试信号会被“系统跑飞”淹没。

### 3.3 一次异常与一次中断的对比

| 维度 | 异常（如断点、非法指令） | 中断（如时钟） |
|---|---|---|
| 触发方式 | 同步：由当前指令引起 | 异步：由外部定时器引起 |
| `sepc` 指向 | 触发异常的指令本身 | 被打断的指令（下一次继续执行它） |
| 返回后 | 必须跳过异常指令，否则重复触发 | 必须回到原指令继续执行 |
| `epc` 处理 | handler 按指令长度前进 2/4 字节 | 不修改 `epc` |
| 典型验证 | Test 1、Test 2 | Test 3 |
| 失败表现 | 死循环、刷屏、跳过指令 | 只收到一次中断、`ticks` 不增长 |

这张表解释了为什么 `exception_handler()` 要推进 `epc`，而 `interrupt_handler()` 不能推进 `epc`：两者的“返回语义”不同。

### 3.4 小结

本章的逻辑可以概括为：

1. **硬件**负责在 Trap 发生时记录 `sepc`、`scause`、`sstatus` 并跳到 `stvec`；
2. **`SAVE_ALL` + `__alltraps`** 负责把现场固化成 Trap frame，并按调用约定交给 C；
3. **`trap_dispatch` + 两个 handler** 负责按 `scause` 分类处理，必要时修改 `tf->epc`、重新上弦定时器；
4. **`RESTORE_ALL` + `sret`** 负责把 Trap frame 写回处理器状态，回到正确的执行流；
5. **临界区**负责在需要原子性的代码段暂时关闭这套机制。

理解了这五步，就理解了“内核如何从一条直线执行流，变成能够被随时打断、又能正确恢复的可抢占执行流”。

#### 模块功能描述

##### 1.1 需要实现/修改的位置

```asm
    .globl __alltraps
    .align(2)
__alltraps:
    SAVE_ALL

    #lab3 function1 2412102
    mv a0, sp
    jal trap
    # sp should be the same as before "jal trap"

    .globl __trapret
__trapret:
    RESTORE_ALL
    # return from supervisor call
    sret
```

本模块不涉及 C 函数签名，涉及的是汇编入口与 C 函数之间的调用关系：

```c
void trap(struct trapframe *tf);   /* kern/trap/trap.h，不可修改 */
```

##### 1.2 功能说明

`__alltraps` 是 S 态 Trap 的统一入口：`idt_init()` 把它的地址写入 `stvec`，硬件在发生中断或异常时把 PC 跳到 `stvec`，于是执行流进入这里。

它要完成的事情只有一件：**把 `SAVE_ALL` 保存好的 Trap frame 地址，按照 RISC-V 调用约定交给 C 语言函数 `trap()`**。

- `SAVE_ALL` 先把陷入前的 `sp` 存入 `sscratch`，再执行 `addi sp, sp, -36 * REGBYTES`，在**当前内核栈**上分配 288 字节的 Trap frame，并逐字保存 32 个通用寄存器和 `sstatus/sepc/sbadaddr/scause` 四个 CSR。
- `SAVE_ALL` 结束后，`sp` 恰好指向这个 Trap frame 的起始地址，而 `struct trapframe` 的字段顺序与之一一对应。所以 `mv a0, sp` 就是把 `struct trapframe *tf` 放进第一个参数寄存器 `a0`。
- `jal trap` 调用 C 函数；`jal` 会把下一条指令的地址写进 `ra`，而 `__trapret` 正好紧跟在后面，因此 `trap()` 返回后会自然落到 `__trapret`，进入 `RESTORE_ALL + sret`。

##### 1.3 与 A、B 的接口契约

| 契约 | 内容 | 违反后的现象 |
|---|---|---|
| `sp` 调用前后不变 | `RESTORE_ALL` 完全依靠当前 `sp` 相对偏移读取 Trap frame；`jal trap` 前后不能对 `sp` 做任何加减 | 所有偏移错位，寄存器恢复成错误的值，Test 1 失败或直接跑飞 |
| `a0` 的指向 | `a0` 必须是 `SAVE_ALL` 之后、Trap frame 起始处的 `sp`，不能是陷入前的栈指针 | `trap()` 读到的是旧栈上的随机数据，`tf->cause` 分类错误 |
| `tf->epc` 的修改 | B 的 `exception_handler()` 修改 `tf->epc`；A 的 `RESTORE_ALL` 必须把它写回 `sepc` | `sret` 回到原指令，同一条异常反复触发 |
| `ra` 被覆盖无害 | 被打断代码原来的 `ra` 已被 `SAVE_ALL` 保存在 offset 8；`RESTORE_ALL` 会恢复 | — |
| `a0` 被覆盖无害 | 原来的 `a0` 已被 `SAVE_ALL` 保存在 offset 80；`RESTORE_ALL` 会恢复 | — |

1. **`__alltraps` 不是被 `call` 进来的**。它是硬件经 `stvec` 跳进来的，没有调用者替它准备栈帧，也没有“返回地址”可言；所以不要在入口处添加 `addi sp, sp, -N` / `sd ra, ...` 这种标准函数序言。

### 练习：`sync.h` 中的 `do {} while (0)`

文件 `code/kern/sync/sync.h`：

```c
#define local_intr_save(x) \
    do {                   \
        x = __intr_save(); \
    } while (0)
#define local_intr_restore(x) __intr_restore(x);
```

#### 5.1 宏是文本替换，不是函数

`#define` 做的是预处理阶段的文本替换。宏体里如果有多条语句，直接展开到使用处时，语句的边界就不受控制。`do { ... } while (0)` 的作用，是把宏体包装成语法上的**一条完整语句**：

- `do` 后面必须跟一个语句（复合语句 `{ ... }` 算一条）；
- `while (0)` 让循环体恰好执行一次；
- 末尾的 `while (0)` 后面不需要分号，使用处照常写一个分号即可，看起来和普通函数调用完全一样。

#### 5.2 解决 `if/else` 被拆散的问题

假设把宏写成裸的花括号：

```c
#define local_intr_save(x) { x = __intr_save(); }
```

下面这段代码：

```c
if (cond)
    local_intr_save(flag);
else
    do_something();
```

会被展开成：

```c
if (cond)
    { flag = __intr_save(); };   // ← 花括号后多出的分号是一条空语句
else                              // ← else 前面不再是一个完整的 if 语句
    do_something();
```

此时编译器会报 `else without a previous if`。原因是 `if (cond) { ... };` 中的 `;` 是一条独立的空语句，`if` 语句在 `;` 处已经结束，`else` 找不到可匹配的 `if`。

用 `do { ... } while (0)` 包起来后：

```c
if (cond)
    do { flag = __intr_save(); } while (0);
else
    do_something();
```

`do ... while (0);` 整体是一条语句，末尾的分号属于这条 `do-while` 语句，不会额外产生空语句，`else` 可以正确匹配。

#### 5.3 `while (0)` 保证只执行一次

`do-while` 是“先执行后判断”的循环。条件为常量 `0`，所以循环体执行一次后立即退出。编译器在优化时会把它消掉，不会带来运行时开销。

#### 5.4 本文件里的反例：`local_intr_restore`

`sync.h` 中另一个宏没有使用 `do {} while (0)`：

```c
#define local_intr_restore(x) __intr_restore(x);
```

宏体自带分号。把它放进同样的 `if/else`：

```c
if (cond)
    local_intr_restore(flag);
else
    do_something();
```

展开后是：

```c
if (cond)
    __intr_restore(flag);;   // ← 宏体自带的分号 + 使用处的分号 = 多一条空语句
else
    do_something();
```

同样会导致 `else without a previous if`。这个反例正好说明：**只有把宏体包成 `do {} while (0)`，宏才能安全地出现在 `if/else`、`for/while` 等只接受单条语句的位置**。

#### 5.5 进一步讨论

- **宏参数要加括号**：通用规则是 `#define M(x) ((x) + 1)`，防止 `M(a + b) * c` 之类的展开优先级错误。本文件里的 `x` 直接作为赋值左值使用，问题不明显，但仍是好习惯。
- **`do {} while (0)` 不是表达式**：它只能用在“语句”位置。如果需要 `y = MAX(a, b)` 这样的表达式宏，不能用 `do-while`，应使用 `({ ... })` 语句表达式（GCC 扩展）或 `static inline` 函数。
- **本实验中的实际用途**：`kern/mm/pmm.c` 的 `page_init`、`page_alloc`、`page_free` 等函数用 `local_intr_save(intr_flag)` 关中断、`local_intr_restore(intr_flag)` 恢复，保证物理页链表操作的原子性。`local_intr_save` 必须能安全地出现在这些函数体的任意语句位置，这正是 `do {} while (0)` 要解决的问题。
- **为什么 `__intr_save` 返回 `bool`**：它记录“进入临界区前中断是否已经开启”。如果之前已经关闭（嵌套临界区），`__intr_restore(false)` 不会误开启中断，从而支持嵌套。

## 六、实验总结与收获

### 6.1 对操作系统的理解

#### 6.1.1 本实验中的知识点与 OS 原理的对应

| 本实验中的东西 | OS 原理中的知识点 | 二者的关系与差异 |
|---|---|---|
| `scause` 最高位为 1/0 分别进入 `interrupt_handler`/`exception_handler` | 中断、异常、系统调用的分类 | 实验只做了“按原因分类并分别处理”。原理中的系统调用还要经过 `ecall`、用户态→内核态、参数校验与返回值传递；本实验的 Trap 全部发生在 S 态，没有完整的 U→S 流程。 |
| `stvec`、`sepc`、`scause`、`sstatus(SIE/SPIE/SPP)`、`sret` | 中断响应的硬件流程、上下文切换 | 原理课上一句“硬件保存现场、跳转到中断处理程序”，在实验里变成了一组具体 CSR 的读写。实验把硬件的隐式行为显式化了，因而更容易看清每一步的因果关系。 |
| `SAVE_ALL` / `RESTORE_ALL` / `struct trapframe` | 进程上下文的保存与恢复 | 实验保存 32 个通用寄存器 + 4 个 CSR，共 288 字节。原理中的进程上下文还包括页表基址、文件描述符、信号状态、调度信息等；实验只覆盖了“处理器现场”这一子集。 |
| `tf->epc` 在异常处理中前进 2/4 字节 | 异常返回与指令重启 | 原理中异常处理后要决定“重启指令”还是“跳过指令”；实验用 `epc` 的显式修改来体现这个决定。中断与异常的区别也在这里：中断返回原指令，异常通常要跳过。 |
| 每 100 个 tick 打印一行 | 时钟中断是分时与时间片的基础 | 实验只累计 `ticks` 并打印，没有进程调度。原理中时钟中断会触发调度器、更新时间片、决定是否切换进程；实验展示了“时钟能周期性打断内核”这一最底层能力。 |
| `local_intr_save/restore` 保护 `alloc_pages` 的空闲链表 | 临界区、原子性、同步互斥 | 实验在单核上用“关中断”实现最小粒度的原子性；原理中还会涉及锁、信号量、条件变量，以及多核下的原子指令与内存屏障。 |
| `sscratch` 暂存旧 `sp`、随后清零 | 内核栈与用户栈的切换、递归异常识别 | 实验只用它保存旧 `sp`；原理中 `sscratch` 常用于保存内核栈指针，实现 U→S 的栈切换。清零后还能帮助识别“Trap 发生在内核态”的递归异常。 |

#### 6.1.2 本实验没有对应上的 OS 原理知识点

1. **进程调度与时间片轮转**
   实验的时钟中断只做计数和打印，没有“选择下一个进程”的调度器。原理中的时钟中断是抢占式调度的触发点：保存当前进程上下文、选择就绪队列中的下一个、切换页表与栈。

2. **用户态陷入内核与系统调用**
   本实验的所有 Trap 都发生在 S 态（内核态），没有 U 态代码，也没有 `ecall`。原理中的系统调用需要：用户态执行 `ecall` → 硬件切换到 S 态 → 内核根据系统调用号分派 → 校验用户指针 → 返回用户态。本实验没有覆盖 U→S 的特权级切换、参数传递和返回值处理。

3. **外设中断、中断控制器与中断优先级/嵌套**
   实验只用了 S 态定时器中断，以及测试代码手工构造的软件中断。原理中的外设中断要经过 PLIC/APIC 等中断控制器，涉及中断屏蔽、优先级、抢占与嵌套；本实验的 `interrupt_handler` 只是一个 `switch`。

4. **虚拟内存与缺页异常**
   本实验的 `pmm` 只管理物理页，内核尚未建立/启用页表。原理中的缺页异常需要：MMU 触发 page fault → 内核分配物理页 → 建立页表项 → 重启指令。本实验的 `exception_handler` 对未列出的异常只做 `print_trapframe` 兜底，没有恢复逻辑。

5. **多核与并发**
   实验是单 hart 执行，“关中断”就足以保证临界区的原子性。原理中的多核系统还需要：自旋锁、原子指令（`amoswap`/`lr-sc`）、内存屏障、每核独立的中断状态。单核的 `SIE` 开关不能保护多核之间的竞争。

6. **信号、进程间通信与文件系统**
   这些都属于更高层的 OS 机制，本实验完全没有涉及。

#### 6.1.3 我的理解

这次实验最深的体会是：**“保存现场”和“恢复现场”不是两段孤立的代码，而是一份由三方共同遵守的契约**。

`SAVE_ALL` 定义了 Trap frame 的布局，`__alltraps` 把它的地址交给 C，`RESTORE_ALL` 再按同一布局读出来。任何一方偏离布局，另外两方都会出错，而且错误往往不会在编译期暴露，而是在运行期表现为“寄存器值莫名其妙”“系统跑飞”“同一条异常反复触发”。这让我理解了为什么操作系统代码里“约定”比“技巧”更重要：`sp` 不变、`epc` 写回、`x2` 最后恢复，这些约束看起来只是几行注释，实际上是整个 Trap 机制能够成立的前提。

另一个体会是**中断与异常的返回语义不同**。时钟中断返回后要继续执行被打断的指令，所以不能改 `epc`；断点和非法指令如果直接返回，会再次执行同一条指令，所以必须让 `epc` 前进。前进多少又取决于指令长度（2 字节压缩指令 vs 4 字节普通指令）。这条“看似琐碎”的规则，实际上是“异常处理如何避免死循环”的核心。

最后，`local_intr_save/restore` 让我第一次具体看到“原子性”是怎么实现的：不是靠硬件魔法，而是靠“在临界区里暂时不响应中断”。而 `__intr_save()` 记录旧状态、支持嵌套的设计，也解释了为什么同步原语要考虑“可重入”和“嵌套”。

### 6.2 AI 协作开发的经验

本实验的三个模块都由 AI 辅助生成，但真正决定成败的不是“生成得快不快”，而是“约束写得全不全、验证做得够不够”。归纳为五条：

#### 6.2.1 提示词必须带“可验证的约束”，不能只描述意图

只写“实现 Trap 入口”或“实现异常处理”，AI 会按最常见、最通用的写法生成代码，而“最常见”未必符合本实验的约束。例如：

- `__alltraps` 如果只写“调用 `trap()`”，AI 会按普通函数的习惯加 prologue/epilogue，改变 `sp`；
- `exception_handler` 如果只写“处理断点”，AI 很可能固定 `epc += 4`，因为它不知道 `ebreak` 在本工具链下是 2 字节的 `c.ebreak`；
- 时钟中断如果只写“计数并打印”，AI 可能忘记 `clock_set_next_event()`，导致只收到一次中断。

有效的做法是把**验收标准**写进提示词：`tools/grade.sh` 里 `grep` 的字符串、`epc` 的步长规则、`sp` 调用前后不变、`SHUTDOWN_AFTER` 的最小值、注释与学号的保留要求。约束越具体，AI 的自由发挥空间越小，返工越少。

#### 6.2.2 AI 会漏掉“隐含前提”，需要人先读骨架

有几处关键信息在代码里没有显式写出，AI 也不会主动去确认：

- `SHUTDOWN_AFTER` 在 `trap.c` 和指导书里都没有定义，需要自己 `#define`，而且取值不能太小（`ticks=200` 的那次打印发生在 handler 里，取值 2 会在测试观察到 200 之前就关机）；
- `ebreak` 被汇编成 2 字节的 `c.ebreak`，这是工具链行为，不是源码里能直接看到的；
- `__alltraps` 是硬件经 `stvec` 跳入的，不是被 `call` 调用的，因此没有“调用者准备的栈帧”；
- `local_intr_restore` 宏体自带分号，正好是 `do {} while (0)` 的反例，这个细节需要人读 `sync.h` 才能发现。

这些“隐含前提”是人和 AI 协作时最容易出问题的地方。人的价值不在于写得更快，而在于**先读代码、先确认前提，再把前提写进提示词**。

#### 6.2.3 验证比生成更重要

AI 生成代码只是起点。真正让代码收敛的是三类验证：

1. **静态验证**：`make obj/kern/trap/trapentry.o` 能否单独编译；`objdump` 的指令序列是否符合预期（例如 `SAVE_ALL` 之后是否恰好是 `mv a0, sp` 和 `jal trap`）；
2. **行为验证**：`make qemu` 能否看到一行行 `100 ticks`；`make grade` 的 Test 1/2/3 分别暴露哪类问题；
3. **日志验证**：失败时看 `.qemu.*.out` 的串口日志，而不是只看“总分”。

本实验里 `make grade` 的分项信息非常有价值：Test 1 失败通常指向 `RESTORE_ALL` 或 `epc` 步长；Test 2 失败通常指向输出格式或 handler 兜底；Test 3 失败通常指向 `clock_set_next_event()` 或 `SHUTDOWN_AFTER`。把“失败信息”当成反馈信号，比反复让 AI“再生成一版”有效得多。

#### 6.2.4 人负责“跨模块契约”，AI 只看局部

AI 通常只被要求改一个函数或一个宏，它看不到跨模块的约定：

- `__alltraps` 的 `sp` 不变量是它与 `RESTORE_ALL` 之间的契约；
- `tf->epc` 的写回是 `exception_handler` 与 `RESTORE_ALL` 之间的契约；
- Trap frame 的偏移是汇编与 C 之间的契约。

这些契约必须由人来定义、写进各自的提示词，并在合并时复核。本实验的分工方式（A 写 `RESTORE_ALL`、B 写 handler、C 写 `__alltraps`）让每个模块都能单独生成，但**能否拼成一个闭环，取决于契约是否一致**，而不是取决于每个模块单独写得多好。

#### 6.2.5 用最小代价验证集成，而不是等“全部写完再跑”

本次在临时 worktree 里合并 `lab3-A`（已含 B 的实现）并运行 `make grade`，在不改动工作区、不干扰其他分支的前提下，先确认了 C 的 `__alltraps` 与 A/B 的代码能够拼成完整闭环（100/100）。这种“隔离验证”的做法有三个好处：

- 不会把别人的未完成代码混进自己的工作区；
- 失败时能快速判断是“自己的模块”还是“集成问题”；
- 通过后可以把验证结论（而不是猜测）写进报告。

总结成一句话：**AI 擅长“按约束生成”，人擅长“发现约束、定义契约、验证结果”**。把这三件事做好，AI 协作的效率才是真实的；只让 AI 生成而不验证，生成的代码越多，返工越贵。
